-- Buffer Persistent / Gestion de plusieurs Buffer --

. Dans quels cas c'est utile ? 
	- Si j'ai besoin d'avoir plusieurs format d'instances
	- Collection avec durée de vie différentes (entre différente scène)

. Est ce que j'aurais besoin de créer plusieurs buffers d'instances de rendu ? Cas d'utilisation de plusieurs buffers d'instances ?
. Si c'est un buffer interne persistent comment gérer les accès concurrent ? (Lock ?; Lock-free ?)
. Buffer interne avec allocateur custom ? renvoie des handles qui contiennent la range allouer ?

. Piste retenue : gros buffer GPU persistant avec un allocateur interne de régions (sous-allocation).

	Quand on demande un buffer d'instances, l'allocateur réserve une région du gros buffer et retourne un handle.
	Quand on libère cette allocation, la région redevient disponible ; le gros buffer GPU reste alloué.
	Le handle permet de retrouver l'offset et la capacité en octets, ainsi que le nombre d'instances utilisées.

. Plusieurs formats d'instances peuvent cohabiter dans cette même arène : chaque région contient son propre format.

	Le bind group référence uniquement la région de l'allocation via un BufferBinding :
	buffer = le gros buffer, offset = début de la région, size = taille de la région.
	Le shader voit cette région comme son tableau d'instances, avec le format attendu par le pipeline.
	Les indices de dessin sont locaux à la région liée (0..len pour toute la collection).

. Garder une API publique composée de fonctions ; l'arène, l'allocateur et les objets GPU restent internes.

-- Piste à affiner : arène de buffers par pages --

. Remplacer le principe du buffer GPU unique qui grossit par plusieurs pages, chacune contenant un buffer GPU de capacité fixe.

	L'allocateur cherche une région libre assez grande dans les pages existantes, en respectant l'alignement.
	Si aucune page ne convient, il ajoute une page sans déplacer les allocations existantes.
	Une allocation plus grande que la capacité habituelle d'une page pourrait avoir une page dédiée.

. Le handle permet de retrouver la page, l'offset, la capacité et le nombre d'instances utilisées.

	Piste : handle générationnel opaque vers une table CPU d'allocations, dont chaque entrée contient ces informations.
	Pour écrire ou créer un binding, on résout le handle puis on récupère le buffer de la page correspondante.

. Ajouter une page ne demande pas de reconstruire les bind groups existants : les buffers qu'ils référencent restent les mêmes.

	Un bind group référence un buffer GPU précis, un offset et une taille, pas le champ « buffer courant » de l'arène.
	À l'inverse, remplacer un buffer par un autre impose de recréer les bind groups concernés, même si les offsets sont conservés.
	Les handles CPU peuvent rester valides via l'indirection, mais cela ne met pas automatiquement à jour les bind groups.

. Organisation des bindings à décider :
	- Un bind group par allocation, qui référence directement sa région dans le buffer de sa page.
	- Un bind group par page avec offset dynamique, si le layout et la taille de binding le permettent.
	- Pour un storage buffer, possibilité de sélectionner les données par un index dans la plage liée.
	Changer de page peut nécessiter de changer de bind group ; respecter les limites de taille des bindings et les alignements.

. Première version possible : allocation en fin de page, ajout de pages au besoin, aucun déplacement.

	Ajouter ensuite la réutilisation des régions libérées via une liste de plages libres.
	Prévoir que plusieurs pages peuvent augmenter les changements de bind groups pendant le rendu.
	Une éventuelle compaction ou le déplacement d'une allocation qui dépasse sa capacité nécessitera de mettre à jour les bindings concernés.
	La réutilisation des régions doit aussi tenir compte des commandes GPU qui utilisent encore leurs données.

. Cette architecture reste une piste à affiner, sans implémentation pour l'instant.
